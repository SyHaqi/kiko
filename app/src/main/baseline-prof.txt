# Baseline profile — hand-seeded, not device-generated.
#
# What this file is: a list of classes/methods ART should compile ahead-of-time and
# keep warm, instead of interpreting/JIT-compiling them from scratch on first use.
# AGP compiles this into a binary .prof at build time and packages it into the APK;
# androidx.profileinstaller (added in build.gradle.kts) installs it on the device.
#
# Why it's here: on a fresh release install, Compose's lazy-list, animation, and
# recomposition machinery — plus Coil's image pipeline — are cold. The first several
# times DetailScreen scrolls, those code paths are still being interpreted rather than
# running compiled, which reads as jank indistinguishable from a real perf bug, and
# fades after repeated use as ART's own runtime profiling catches up on its own.
# This file just gives ART a head start on exactly that code, from install.
#
# Caveat: this is a best-effort seed, not a measured profile. It's hand-picked based on
# what DetailScreen/StaggeredItem/scrolling actually exercise (see DetailScreen.kt,
# Motion.kt) — not captured from a real run on a device. There is deliberately no
# on-device automation (Macrobenchmark/UiAutomator module or script) generating or
# refreshing this file; it's a static, hand-maintained file you edit directly when
# the app's startup/scroll-heavy code changes.
#
# Format: each line is either a bare class (kept resident) or an HSPL-prefixed method
# wildcard (H = hot, S = startup, P = post-startup — compiled ahead-of-time for all
# three). Lines AGP can't resolve at build time are silently skipped, not a build
# failure, so this is safe to ship even if a given method wildcard doesn't match
# anything on your current dependency versions.

# --- Your app's own code: everything under com.kiko.tracker, so the compiler doesn't

# (Note: HSPL flags are only valid on method rules, not class wildcards like this one —
# the unflagged class rule below is the correct form and covers the same intent.)
